# tc を用いた MAP-E NAPT の実装メカニズム

MAP-E（v6 プラスや OCN バーチャルコネクトなど）環境において Linux ルーターを自作・構築する際、まさにその「非連続なポートレンジ」と「Netfilter（iptables/nftables）の制約」が最大の壁になります。

Netfilter の SNAT や Masquerade は、単一の連続したポートレンジ（例: 10000-10255）からのポート割り当てしかサポートしておらず、PSID に基づく飛び飛びのポート群を直接扱うことができません。

この制約をカーネルモジュールの改造なしに突破する賢い対処法として知られているのが、Netfilter（ステートフル）と tc（ステートレス）を組み合わせた 2 段階のポート変換です。

## 手法の核となるアイデア

この手法の核となるアイデアは、次のとおりです。

**「Netfilter には連続したダミーのポートレンジを扱わせ、その前後で tc（Traffic Control）を使ってダミーポートと実際の MAP-E ポートをステートレスに相互変換する」**

## 1. 全体アーキテクチャ（2 段階変換）

パケットの処理フローは、以下の 2 つのフェーズに分かれます。

ここでは、CE に割り当てられた利用可能ポート数が 256 個であると仮定します。

1. フェーズ 1（ステートフル）: Netfilter が、LAN 内のプライベート IP/ポートと、連続した 256 個のダミーポート（例: 10000〜10255）の間で通常の NAPT を行います。
2. フェーズ 2（ステートレス）: tc が、ダミーポートと、実際に割り当てられた非連続な 256 個の MAP-E ポートの間で、1 対 1 のアルゴリズムに基づく直接変換を行います。

## 2. パケットの処理フロー

Linux のネットワークスタックにおけるフックの順序（`tc ingress -> Netfilter -> tc egress`）を利用して実装します。

### 送信時: LAN からインターネットへ（Egress）

1. Netfilter（Postrouting）
   送信元ポートを連続したダミーポートレンジ（例: 10000-10255）のいずれかに書き換えます。このとき Netfilter はセッション情報を Conntrack に記録します。

2. tc（Egress）
   送信元インターフェースのキューイング規則（qdisc）でパケットを捕捉します。送信元ポートがダミーポートレンジ内であれば、MAP-E の PSID 計算式に基づいて実際の非連続な MAP-E ポートに書き換えます。同時に TCP/UDP のチェックサムを再計算します。

3. カプセル化
   MAP-E のルールに従い、IPv6 でカプセル化されて WAN へ送信されます。

### 受信時: インターネットから LAN へ（Ingress）

1. 非カプセル化
   IPv6 から IPv4 パケットを取り出します。

2. tc（Ingress）
   受信インターフェースの tc でパケットを捕捉します。宛先ポートが自分の MAP-E ポートに合致する場合、送信時の逆算を行い、宛先ポートをダミーポートへ書き換えます。チェックサムも再計算します。

3. Netfilter（Prerouting）
   パケットが Netfilter に到達すると、宛先ポートはすでにダミーポートに戻っているため、Conntrack の記録と一致します。標準の DNAT 機能により、LAN 内の正しいプライベート IP/ポートへ変換されルーティングされます。

## tc での具体的なポート書き換え手法

tc でポートとチェックサムを書き換える手法には、主に以下の 2 つがあります。

### アプローチ A: tc-bpf（eBPF）を使用する（現在主流・推奨）

tc の clsact qdisc に eBPF プログラムをアタッチしてパケットを処理します。C 言語ライクに記述できるため、MAP-E の複雑なビットシフトやポート計算を容易に実装できます。

- メリット: 計算ロジックの自由度が高く、チェックサムの再計算（`bpf_csum_diff` など）もカーネルのヘルパー関数を呼び出すだけで安全かつ高速に行えます。
- 実装例: ダミーポートからインデックス（0〜255）を引き出し、PSID と組み合わせて以下のようなロジックで実際のポートを算出します。

$$
P_{mape} = (\text{Offset}) + (\text{Index} / \text{BlockSize}) \times \text{Shift} + \text{PSID} \times \text{Multiplier}
$$

### アプローチ B: tc-pedit を使用する（レガシー）

eBPF が普及する前に使われていた力技です。tc filter の action pedit モジュールを使って、パケットヘッダの特定のオフセットの生バイトを直接書き換えます。

- デメリット: MAP-E のポート計算は「16 ポートずつのブロックが複数」といった構造になるため、計算式をそのまま pedit に落とし込むことはできません。
- 結果として、ポートのブロック数だけ（例えば 16 個の）大量の tc filter ルールを手書き（またはスクリプトで生成）して並べる必要があり、運用が非常に煩雑になります。

## この実装手法のメリット

- 標準カーネルで動作可能: カスタムパッチを当てた Netfilter モジュール（OpenWrt などで使われる nat46 やカスタム xt_NAT など）をコンパイルする必要がなく、標準的な Linux ディストリビューションでそのまま動作します。
- Conntrack の恩恵: コネクション管理やステートフルな処理、ALG（Application Layer Gateway）などはすべて枯れて安定した Netfilter に任せることができるため、ルーターとしての安定性が保たれます。
